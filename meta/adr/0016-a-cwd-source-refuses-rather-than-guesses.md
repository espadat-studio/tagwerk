# A cwd source refuses rather than guesses

`omarchy-cmd-terminal-cwd` solves the same problem on the same machine and resolves an ambiguous terminal with `pgrep -P "$terminal_pid" | tail -n1`, taking whichever child the kernel happens to list last. tagwerk filters the direct children of the focused window's pid to those whose `exe` appears in `/etc/shells`, and resolves a cwd only when exactly one candidate remains. The asymmetry is deliberate: a wrong cwd resolves to a wrong repo and lands on an invoice, where an absent cwd falls through to the ambient bucket or `personal/other` and the reports show it as exactly that. `tail -n1` is the right answer for a terminal launcher picking a directory to start in, and the wrong one for a number a client is billed for. Measured across the three focusable terminals running on this machine, each had exactly one login-shell child, so refusing costs nothing in the common case: ambiguity needs several tabs or splits inside one OS window, which is precisely the case where the kitty socket answers exactly and is tried first.

Rejected: mirroring `tail -n1`, which is one branch shorter and matches the reference implementation a reader will inevitably compare this against, but books a kitty window holding three tabs in three repos to whichever shell the kernel lists last, silently and differently on each poll. Rejected: splitting the minute across every candidate shell, attractive because `attribute` already splits a present minute evenly across leased repos so the machinery exists, but a lease is evidence that a repo was actually worked in, where two sibling shells are one terminal of which the user can only see one.

Consequences: the `/etc/shells` guard removes any need for a list of terminal window classes, which is why `window_class == "kitty"` could be deleted outright rather than grown — a browser or Electron window has no login-shell child and excludes itself. A shell running under tmux, screen or any other wrapper is not a direct child of the terminal, so those windows resolve to nothing; the kitty socket path is unaffected because it reports the pane's own foreground process, and it is tried first for that reason. `/etc/shells` grows as packages register a shell, so the guard is self-maintaining for anything pacman installed and blind to a shell built by hand. A window whose process exits between the `hyprctl` call and the `/proc` read resolves to nothing rather than raising, because that race is ordinary rather than a fault.
